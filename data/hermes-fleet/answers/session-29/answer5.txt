Here's a ten-point orientation for a new contributor, each pointing at the one file:line to start from.

1. The whole scheme is hidden behind one interface, so engines never touch crypto. Read `api/src/main/java/org/apache/iceberg/encryption/EncryptionManager.java` (the `encrypt`/`decrypt` methods) first.

2. Iceberg stores only key references and opaque `key_metadata` in metadata, never raw keys — the spec's minimal ledger. Read `EncryptedKeyParser.java:36-64` (`key-id` / `encrypted-key-metadata` / `encrypted-by-id` / `properties` JSON).

3. Table-level on/off and config live in table properties, not in engine code. Read `TableProperties.java:459-464` (`encryption.key-id`, `encryption.data-key-length`) and `EncryptionUtil.createEncryptionManager` `EncryptionUtil.java:101-123` (which returns `PlaintextEncryptionManager` when unset).

4. Real crypto (AES-GCM, nonce, tag, key-length checks) is isolated in one class. Read `Ciphers.java:32-48` (block size, nonce, tag) and `Ciphers.java:175-179` (the single `AEADBadTagException` failure mode for wrong-key/tampered data).

5. Envelope encryption and rotation are driven by the KMS client, not core. Read `KeyManagementClient.java:27-73` (`wrapKey`/`unwrapKey`/`generateKey`) and `StandardEncryptionManager.keyEncryptionKeyID()` `StandardEncryptionManager.java:135-160` (730-day KEK lifespan, NIST SP 800-57).

6. Per-file keys are generated at write time and embedded into each file's stream. Read `StandardEncryptionManager.StandardEncryptedOutputFile.keyMetadata()` `StandardEncryptionManager.java:262-293` and `AesGcmOutputStream.java:137-165` (header, block encryption, AAD).

7. Files get decrypted lazily and in batch at read time. Read `EncryptingFileIO.bulkDecrypt()` `EncryptingFileIO.java:71-90` and the shared `InputFilesDecryptor` `InputFilesDecryptor.java:36-58`.

8. The manifest list / snapshot `key-id` (the spec's snapshot field) flows through `ManifestListWriter.encryptionKeys()` `ManifestListWriter.java:100-111` → `registerKeyMetadata` `StandardEncryptionManager.java:204-218` → `SnapshotProducer.java:359-372`, then `SnapshotParser.java:110` writes JSON `key-id`.

9. The `encryption-keys` list in table metadata is built/updated through the builder, deduped on commit retries. Read `TableMetadata.addEncryptionKey` `TableMetadata.java:1507-1519` and `SnapshotProducer.java:507-510`.

10. Engines consume it through one seam: `EncryptingFileIO.combine(io, table.encryption())`. Read `BaseReader.java:94` (Spark) and `FlinkInputFormat.java:117` + `DataIterator.java:52-59` (Flink), and verify end-to-end in `spark/.../sql/TestTableEncryption.java:64-90`.

One thing to keep in mind: encryption properties are a v3+ feature — `EncryptionUtil.checkCompatibility` `EncryptionUtil.java:205-217` rejects them for format versions below 3, so a new feature touching this must respect that version gate.
