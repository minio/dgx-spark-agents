I read MetadataTableUtils.java plus every metadata table class and scan base it instantiates. Here's how the implementation maps to the format spec.

Important framing first: the format spec never defines queryable "metadata tables" — those are an engine-side feature of the Java implementation. But every row these tables return is a projection of an on-disk structure the spec *does* define. So "follows the specification" here means: the code exposes each spec-defined metadata structure as a read-only table, and reuses the spec's scan-planning rules to read them.

## 1. Registration and wiring — MetadataTableUtils

- `hasMetadataTableName` (MetadataTableUtils.java:28-30) and `MetadataTableType.from` (MetadataTableType.java:41-47) match a trailing name segment (`.files`, `.snapshots`, etc.) to one of 16 enum values (MetadataTableType.java:23-39).
- The factory switch (MetadataTableUtils.java:56-95) picks a concrete table per type. The name is derived as `<table>.<lowercased type>` (MetadataTableUtils.java:109-111).
- Base tables vs. catalog-backed tables are normalized to a `BaseTable` (MetadataTableUtils.java:32-54) so the metadata table always reads through `TableOperations` — which is how it reaches the committed metadata file (`refresh()` delegate in BaseMetadataTable.java:155-157).

## 2. The read-only, snapshot-consistent base — BaseMetadataTable

- Extends `BaseReadOnlyTable` (BaseMetadataTable.java:43). Matches the spec's core promise: reads use a committed snapshot and readers take no locks (spec.md:71, 93).
- Snapshot-related state is delegated straight through to the underlying table: `currentSnapshot`, `snapshots`, `snapshot(id)`, `history`, `refs` (BaseMetadataTable.java:190-222). These mirror the spec's table-metadata `snapshots`, `snapshot-log`, and `refs` fields (spec.md:1161-1167).
- `supportsTimeTravel` gating (BaseMetadataTable.java:44-52, 121-123): only single-snapshot tables (entries, files, manifests, partitions, position_deletes) support `useSnapshot`/`asOfTime`; the others span all snapshots and are handled by `BaseAllMetadataTableScan`, which throws for time-travel/ref selection (BaseAllMetadataTableScan.java:48-60).

## 3. Scan planning follows the spec's rules

The scans apply the spec's Scan Planning algorithm (spec.md:1053-1093) rather than reading metadata cursor-style:

- **Per-manifest partition-spec filter.** `transformSpec`/`transformSpecs` (BaseMetadataTable.java:83-117) build a fake partition spec that rewrites a filter on the metadata table's `partition` column into partition predicates via an identity transform — the spec's *inclusive projection* (spec.md:1059-1063). It deliberately drops non-partition predicates.
- **Manifest skipping via partition summaries.** `BaseFilesTable.planFiles` (BaseFilesTable.java:59-87) and `BaseEntriesTable.planFiles` (BaseEntriesTable.java:65-98) build a `ManifestEvaluator` keyed by the manifest's `partitionSpecId()` and skip manifests whose field summaries can't match. This is the spec's "manifests that contain no matching files, determined using file counts or partition summaries, may be skipped" (spec.md:1057) and its "reads use the specs stored in manifest files" (spec.md:1156-1158).
- **Residual handling.** `ignoreResiduals` swaps the filter for `alwaysTrue` and each task carries a `ResidualEvaluator` (BaseFilesTable.java:82; BaseEntriesTable.java:93) — the residual between the inclusive projection and the actual predicate.
- **Parallel planning.** `BaseAllMetadataTableScan.reachableManifests` walks all snapshots in parallel and dedups into a set (BaseAllMetadataTableScan.java:74-86) — consistent with the spec's "job planning handled primarily by clients," not a central store (spec.md:73). `PartitionsTable` similarly aggregates entries with a `ParallelIterable` (PartitionsTable.java:229-233).

## 4. Each table is a projection of a spec structure

- **Files tables** (`FilesTable`, `DataFilesTable`, `DeleteFilesTable`, `All*FilesTable`): schema built from `DataFile.getType(partitionType)` (BaseFilesTable.java:47-57) — i.e. the spec's `data_file` struct (spec.md:713-745): `partition`, `record_count`, `file_size_in_bytes`, bounds maps, `content`, `sort_order_id`. The manifests() override selects data vs delete manifests per table (FilesTable.java:60-62, DataFilesTable.java:60-62, DeleteFilesTable.java:60-62). `ManifestReadTask` opens the manifest and projects entries (BaseFilesTable.java:183-185), and `estimatedRowsCount` sums the manifest list's added/existing/deleted counts (BaseFilesTable.java:177-181) — exactly the manifest-list summary fields (spec.md:1021-1026). The All-* variants iterate every reachable snapshot (`AllDataFilesTable.java:66-68`) = "files valid in any snapshot not yet expired," matching the spec's file-lifetime rule (spec.md:1162).
- **Entries tables** (`ManifestEntriesTable`, `AllEntriesTable`): schema from `ManifestEntry.getSchema` (BaseEntriesTable.java:53-63), i.e. the spec's `manifest_entry` struct — `status`, `snapshot_id`, `sequence_number`, `data_file` (spec.md:686-711). It additionally filters manifests by `content` with `ManifestContentEvaluator` (BaseEntriesTable.java:83-91, 253-283) so `data_file.content` predicates prune correctly (spec.md:720). The class warns it exposes "files that have been deleted" — i.e. entries with `status=DELETED`, which the spec says are informational and not used in scans (spec.md:691, 1055).
- **Manifests table** (`ManifestsTable`): a static schema mirroring the spec's `manifest_file` struct (ManifestsTable.java:31-53): `content`, `path`, `length`, `partition_spec_id`, `added_snapshot_id`, per-content added/existing/deleted counts, and `partition_summaries` = `field_summary` (`contains_null`, `contains_nan`, `lower_bound`, `upper_bound`, spec.md:1031-1038). `manifestFileToRow`/`partitionSummariesToRows` decode the byte-encoded bounds with `Conversions.fromByteBuffer` and `transform.toHumanString` (ManifestsTable.java:101-148). This is the spec's manifest list as a table (spec.md:89, 1005).
- **AllManifestsTable**: extends this across all snapshots and, when a snapshot has a manifest list, reads that manifest list directly as an Avro data file (AllManifestsTable.java:196-219) — the spec states the manifest list "is a valid Iceberg data file" (spec.md:1007). Adds `reference_snapshot_id` and filters snapshots with `SnapshotEvaluator` (AllManifestsTable.java:128-131, 307-459).
- **SnapshotsTable**: static schema mirroring the spec's `snapshot` object — `committed_at`, `snapshot_id`, `parent_id`, `operation`, `manifest_list`, `summary` (SnapshotsTable.java:30-40; spec.md:953-966). `planFiles` is overridden to skip the "must have a current snapshot" check because this table spans all snapshots (SnapshotsTable.java:89-94).
- **HistoryTable**: matches the spec's `snapshot-log` (spec.md:1163, 2077-2080). `is_current_ancestor` is computed from `SnapshotUtil.currentAncestorIds` (HistoryTable.java:98-115).
- **MetadataLogEntriesTable**: reads `previousFiles()` (the spec's `metadata-log`, spec.md:1164) plus the current file, and derives `latest_snapshot_id` via `snapshotIdAsOfTime` (MetadataLogEntriesTable.java:60-74, 105-123) — the lookup the spec prescribes for point-in-time reads (spec.md:2080).
- **RefsTable**: mirrors the spec's `refs` map and snapshot-reference object — `name`, `type`, `snapshot_id`, `max_reference_age_in_ms`, `min_snapshots_to_keep`, `max_snapshot_age_in_ms` (RefsTable.java:33-40, 95-105; spec.md:1107-1114).
- **PartitionsTable**: aggregated per partition from live manifest entries grouped by `StructLikeMap` (PartitionsTable.java:197-247), with `Partition.update` tallying record/file counts split by `content()` (PartitionsTable.java:331-360). Its columns (`spec_id`, `record_count`, `file_count`, `total_data_file_size_in_bytes`, pos/equality delete counts, `last_updated_*`) mirror the spec's *partition statistics file* schema (spec.md:1258-1295). Note this table computes the aggregates fresh from manifests rather than reading the optional partition-statistics file — matching the spec's allowance that such stats "can also be computed on demand" (spec.md:1241).
- **PositionDeletesTable**: maps to position delete files/deletion vectors (spec.md:1356-1389). Schema uses the reserved metadata columns `delete_file_path`, `delete_file_pos`, `row`, plus `partition`, `spec_id`, and v3-only `content_offset`/`content_size_in_bytes` for DV blobs (PositionDeletesTable.java:114-200). The scan reads delete manifests, filters for `FileContent.POSITION_DELETES`, applies filters via transformed specs on the deletes table and *inclusive projection* for the base-table filter, and emits `PositionDeletesScanTask`s (PositionDeletesTable.java:260-372).

## 5. Where the spec is silent, the code fills gaps — and it stays faithful

The spec says almost nothing about metadata tables, so the implementation has freedom in *what columns to surface*, but it reuses spec-defined field ids and names for the structures it exposes (e.g., the reserved metadata column ids in PositionDeletesTable.java:119-159 match spec.md:452-454). Two deliberate divergences worth flagging:

- `statisticsFiles()`/`partitionStatisticsFiles()` return empty (BaseMetadataTable.java:210-217), even though `PartitionsTable` exists — consistent with the spec marking these informational and not required for reading (spec.md:1238-1241).
- Metadata tables are `Serializable` and serialize to `SerializableTable.copyOf` (BaseMetadataTable.java:234-236) so they can ship to executors without catalog calls — a direct realization of the spec goal that scan planning happen in clients, not against a central store (spec.md:73).

Bottom line: the implementation doesn't add a new metadata *format*; it projects the spec's existing metadata tree (manifest_entry/data_file structs, manifest_file/field_summary, snapshot, snapshot-log, metadata-log, refs, partition statistics, position deletes) into queryable reads, and applies the spec's own scan-planning machinery — per-manifest partition-spec filter projection, summary-based manifest skipping, sequence numbers, and live-only file tracking — to read them.
