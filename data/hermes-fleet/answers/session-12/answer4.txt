Here's how the Spark and Flink integrations hook metadata tables into actual query/planning paths. Query engines don't read the spec files directly — they load a metadata table as a regular Iceberg table (a `MetadataTableUtils` instance), then push Spark/Flink operators on top of the resulting `Dataset`/`RowDataStream`.

## 1. Name resolution: turning `db.tbl$snapshots` / `db.tbl.snapshots` into a metadata table

- **Spark** (`SparkCatalog.loadPath`, spark/v4.1/.../SparkCatalog.java:969-1003): the path tokens after the table location are scanned; any token that `MetadataTableType.from(meta) != null` matches is treated as the metadata-table name (SparkCatalog.java:975-977). It's then appended to the base identifier (SparkCatalog.java:1002) and loaded through the catalog as `tables.load(...)`. So `.../tbl$snapshots` becomes a metadata table read by the same catalog loader — the engine goes through Iceberg's normal table resolution, and the catalog/`MetadataTableUtils` produces the right concrete table. (v3.5 has the same logic at its SparkCatalog.java:994.)

- **Flink** (`FlinkCatalog.toIdentifier`, flink/v2.3/.../FlinkCatalog.java:171-185): Flink object names use a `$` separator (`db.tbl$snapshots`). The name is split on `$`; if the second segment `MetadataTableType.from(...) != null`, it's re-mapped into a two-level `TableIdentifier` — the namespace becomes `db.tbl` and the object name becomes the type (FlinkCatalog.java:178-181). Note the guard at :183 throws `IllegalArgumentException` for any other shape, so an unrecognized `$suffix` fails at resolution rather than silently reading user data. `canBeView` (:187-191) also ensures the metadata-table syntax never routes to the view catalog.

## 2. Programmatic access: the engines' shared entry point

Both engines call `MetadataTableUtils.createMetadataTableInstance(table, type)` to materialize the table, then wrap it in their native relation:

- **Spark** helper (spark/v4.1/.../SparkTableUtil.java:684-701): `loadMetadataTable` builds the metadata table, wraps it in a `SparkTable`, and turns it into a `DataSourceV2Relation` so the result is a normal Spark `Dataset[Row]` (`SparkTableUtil.loadMetadataTable`, :689-701). This is the generic bridge the engine uses everywhere.
- **Flink** maintenance operators do the same: `TableReader.open` calls `createMetadataTableInstance` and builds a `MetaDataReaderFunction` over the metadata table's schema/io/encryption (flink/v2.3/.../maintenance/operator/TableReader.java:79-91); `MetadataTablePlanner.open` builds the table for constrained/partitioned planning (flink/v2.3/.../MetadataTablePlanner.java:80-84).

## 3. What engines actually DO with the rows — three real workloads

(a) **Manifest rewriting / compaction (Spark actions).** `RewriteManifestsSparkAction.buildManifestEntryDF` loads `ENTRIES`, filters `status < 2` to keep only live entries, and projects out `snapshot_id`, `sequence_number`, `file_sequence_number`, `data_file` (spark/v4.1/.../actions/RewriteManifestsSparkAction.java:260-268). It joins those entries against the set of manifests being rewritten (`:270-273`). It explicitly filters out `status = 2` (deleted) entries — a direct engine-side application of the spec rule that DELETED entries are informational and ignored in scans (spec.md:691, 1055) and the `sequence_number`/`file_sequence_number` fields the spec adds in v2 (spec.md:693-694). The same "status != 2" live-entry filter drives Spark's migration duplicate-file check (spark/v4.1/.../SparkTableUtil.java:464-473) and the v3.5 entries usage (SparkTableUtil.java:701, 860).

(b) **Orphan-file cleanup (both engines).** To find files that are *not* reachable, engines enumerate every live file via the all-* metadata tables, then delete anything on disk not in that set. Spark's `BaseSparkAction.manifestDF` loads `ALL_MANIFESTS` and can filter by reference snapshot (`all_reference_snapshot_id.isInCollection(snapshotIds)`, spark/v4.1/.../actions/BaseSparkAction.java:183-191). Flink's `DeleteOrphanFiles` drives its scan off `MetadataTableType.ALL_FILES` (flink/v2.3/.../maintenance/api/DeleteOrphanFiles.java:220, 238) — the "any snapshot currently tracked" semantics (AllFilesTable.java:23-29). The engine relies on the all-* variant's cross-snapshot, duplicate-tolerant contract here (BaseAllMetadataTableScan.java:74-86).

(c) **Position-delete / DV rewrite (Spark).** `SparkRewritePositionDeleteRunner.dataFiles` loads `DATA_FILES` and filters by an exact partition tuple (`eqNullSafe` on each `partition.<field>` column, spark/v4.1/.../actions/SparkRewritePositionDeleteRunner.java:128-147). And the whole action is built on `MetadataTableType.POSITION_DELETES` (spark/v4.1/.../actions/SparkRewritePositionDeleteRunner.java:81; also RewritePositionDeleteFilesSparkAction.java:144-145 and tests at :370). So the engine drives the actual data-file rewrite by reading the position-delete entries the spec defines (PositionDeletesTable.java:114-200), then rewrites those files.

## 4. Refinement / planning mechanics the engines inherit

Because each action calls `newScan()`/batch plan on the metadata table, it inherits the core scan-planning guards described earlier: partition-spec-specific `ManifestEvaluator`s, per-manifest summary skipping, and the read-only snapshot-consistent `BaseMetadataTable`. Notably the engine *adds* its own filters on top (e.g. `filter("status < 2")`, `col(AllManifestsTable.REF_SNAPSHOT_ID.name()).isInCollection(...)`) — these are pushed down into the metadata table's scan and evaluated with its residual/filter machinery (BaseMetadataTableScan.java, StaticTableScan.java:52-54), so the parallel manifest skipping in BaseFilesTable/BaseEntriesTable applies to the engine's filtering too.

## 5. Serialization to executors

Both engines run planning on the driver and rows on executors, so `BaseMetadataTable` must round-trip through serialization. The `writeReplace → SerializableTable.copyOf` path (BaseMetadataTable.java:234-236) rebuilds on the far side as a full metadata table via `MetadataTableUtils.createMetadataTableInstance` (SerializableTable.java:455-457), and the read-only `operations()` throws (SerializableTable.java:460-463) so executors can't mutate. Spark tests this explicitly across all types (spark/v4.0/.../TestTableSerialization.java:209-210), as does Flink (flink/v2.3/.../TestTableSerialization.java:85-88).

## Summary

The engine-side contract is: **catalog/name resolution recognizes a trailing `$type` token and maps it to a `MetadataTableType` (SparkCatalog.java:975, FlinkCatalog.java:178); a shared helper materializes it as a `Table` (SparkTableUtil.java:691, TableReader.java:80); and the engine then runs normal Spark/Flink operators over the resulting Dataset/stream.** The heaviest consumers are maintenance-style workloads — manifest compaction, orphan-file detection, and position-delete rewrite — which rely on the `ENTRIES` (with live-entry filtering), `ALL_MANIFESTS`/`ALL_FILES`, `DATA_FILES`, and `POSITION_DELETES` metadata tables, because those give the engine a queryable, filterable view of the exact on-disk metadata that the format spec defines.
