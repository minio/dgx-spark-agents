## How the implementation follows the spec

The spec defines a sort order as: an id, plus an ordered list of sort fields, each with a source column id, a transform, a direction (asc/desc), and a null order (nulls-first/nulls-last), with id 0 reserved for unsorted. The implementation mirrors that almost field-for-field.

### Core data model — `SortOrder.java`
- **Fields match the spec's structure.** `SortOrder.java:45-47` holds exactly `schema`, `orderId`, and `fields[]`. The id is a plain `int` (`orderId()`, line 63) and fields are stored as an ordered array (line 54), so list order = sort precedence, as the spec's "order of the sort fields defines the order in which the sort is applied" requires (spec.md:643).
- **Sort field is four attributes, one per spec item.** `SortField.java:28-31` holds `Transform transform`, `int sourceId`, `SortDirection direction`, `NullOrder nullOrder` — precisely the source-column-id, transform, direction, and null-order from spec.md:643-648.
- **Id 0 reserved for unsorted.** `SortOrder.UNSORTED_ORDER` is built with `orderId = 0` and no fields (`SortOrder.java:42-43`). `isSorted()`/`isUnsorted()` are defined purely by whether there's at least one field (`SortOrder.java:73-80`), and the builders hard-enforce the reservation: an order with fields cannot be id 0 ("Sort order ID 0 is reserved for unsorted order", `SortOrder.java:277-279`), and an empty order must be id 0 ("Unsorted order ID must be 0", line 271-273). New orders default to id 1 ("default ID to 1 as 0 is reserved for unsorted order", line 282). The same rules are duplicated in the unbound path (`UnboundSortOrder.java:107-120`).

### The builder enforces "source type must be primitive" and transform validity
Spec: source columns must exist and be effective, and the sort only makes sense if the transform can handle the type (spec.md:645-646; and the "not contained in a map or list" / primitive requirement). `addSortField` binds the term to the schema and pulls the field id (`SortOrder.java:249-251`). `checkCompatibility` (`SortOrder.java:298-313`) then validates each field: the source column must exist (`sourceType != null`, 301), it must be a primitive type ("Cannot sort by non-primitive source field", 303-306), and `transform.canTransform(sourceType)` must be true (307-311). These are the boundary validations the spec calls for.

### Serialization matches the spec's JSON exactly — `SortOrderParser.java`
Appendix C (spec.md:1743-1773) specifies fields `order-id`, `fields`, and per-field `transform`, `source-id`, `direction`, `null-order`. The parser uses exactly those keys (`SortOrderParser.java:33-38`) and writes each field with `transform`, `source-id`, `direction`, `null-order` (`toJsonFields`, 66-78). Direction is emitted lowercase `asc`/`desc` (58-60) and null order as `nulls-first`/`nulls-last` (62-64) — matching the spec's possible-values table (spec.md:1772-1773). Parsing reads `transform` as a string, `source-id` as an int, and resolves `direction`/`null-order` case-insensitively via `SortDirection.fromString` and `toNullOrder` (`SortOrderParser.java:157-166`, `170-179`). This is Iceberg's custom-parser (not Jackson annotations) approach the project mandates.

### Ignoring unknown transforms while still reading — the forward-compat clause
The spec requires readers to ignore unknown transforms (spec.md:1766). This is why analysis is split into **unbound** vs **bound**:
- `SortOrderParser.fromJson` parses to an `UnboundSortOrder`, deferring the schema-dependent work (`SortOrderParser.java:137-144`).
- `UnboundSortOrder.bind` (`UnboundSortOrder.java:40-55`) resolves each transform string against the schema via `Transforms.fromString(sourceType, ...)` per task and `UnboundSortOrder.bindUnchecked` (57-65) skips compatibility validation — used by `fromJson(..., defaultSortOrderId)` when the id doesn't match the default (`SortOrderParser.java:119-127`). So an order with an unknown transform can still be loaded and represented (transform held as a token in `UnboundSortField`, `UnboundSortOrder.java:124-136`), rather than failing the whole table read.

### Order/reusability semantics beyond the literal spec
- `sameOrder`/`equals` compare fields ignoring the id (`SortOrder.java:110-112`, 152-161) — this is the "two sort orders are equivalent by identical fields" concern (spec equivalently defines equivalent partition specs, spec.md:565, and sort orders adopt the same pattern). `toUnbound()` (125-134) round-trips to `source-id`/`direction`/`null-order` for serialization.
- `satisfies` (`SortOrder.java:88-102`): any order satisfies an unsorted one, and a shorter order can't satisfy a longer one — this is the "my order is good enough to claim this order" check used in planning.
- **Order-preserving transforms** implement `satisfiesOrderOf`, the spec's idea that a denser sort (day) implies a coarser sort (month/year). `Dates.java:118-131` checks granularity relationships, and its `preservesOrder()` returns true (113-115). The default on `Transform.java:100-102` is `equals(other)` and `preservesOrder` defaults to false (87-89) — so only genuinely monotonic transforms (identity, dates/timestamps, truncate) claim order preservation. `canTransform` is what `checkCompatibility` leans on.

One nuance to be precise about: the enum constants and their string forms differ slightly from the wire format — `SortDirection.ASC`/`DESC` and `NullOrder.NULLS_FIRST`/`NULLS_LAST` (`SortDirection.java:24-26`, `NullOrder.java:21-23`), with `fromString`/parser doing the lowercased/kebab-case conversion (`SortDirection.java:28-36`, `SortOrderParser.java:58-64`). So the in-memory API uses uppercase enums while the serialized JSON uses the spec's lowercase kebab-case — a clean mapping, no detail lost.

### What the Java code intentionally does *not* implement
The spec's sort order is advisory metadata (spec.md:656: writers "should" use the default but aren't required). Accordingly `SortOrder` is just the shape + validation + serialization: there is no enforcement that files are actually written in that order, and no reference to the per-file `sort_order_id` field here — association to individual data files happens in manifests (`data_file.sort_order_id`, spec.md:740) elsewhere in the codebase. The Java class is the in-memory + (de)serialization model that the rest of the table machinery consumes.
