I traced the production integration paths in both engines. Here's how they use the REST catalog, with file:line.

Both engines plug into the same `RESTCatalog` facade, which is a thin wrapper around `RESTSessionCatalog` (the core client we already examined) bound to an empty session — `RESTCatalog` holds a `RESTSessionCatalog` and exposes it as a plain `Catalog`/`ViewCatalog`/`SupportsNamespaces` (RESTCatalog.java:48-78). So each Spark/Flink SQL statement ultimately funnels into the REST methods I covered earlier (loadTable, commit via POST, etc.).

SPARK (spark/v3.5; same pattern across v4.0/4.1/4.2)
Spark's adapter is `SparkCatalog` (SparkCatalog.java:126). It's catalog-type-agnostic: it builds whatever Iceberg `Catalog` is configured and only checks at initialization whether that catalog is a REST one.
- REST catalog is one of the supported `type` configs, wired through `CatalogUtil.buildIcebergCatalog` (SparkCatalog.java:155-162) — the option docs list `"hive" or "hadoop" or "rest"` (SparkCatalog.java:103-107).
- It detects the REST catalog by instanceof: `this.isRestCatalog = catalog instanceof RESTCatalog` (SparkCatalog.java:798). This flag is used to decide purge behavior: for a REST catalog with `rest-catalog-purge` enabled, the server's delete-with-purge capability is used (`icebergCatalog.dropTable(ident, true)` at SparkCatalog.java:385-393), otherwise Spark deletes reachable files client-side (SparkCatalog.java:395-405). Guard: Preconditions rejects enabling purge on a non-REST catalog (SparkCatalog.java:800-804).
- Table DDL/DML go through the Iceberg catalog API, which the REST client implements: load (loadTable is called at SparkCatalog.java:897, 361, 378), create/build (SparkCatalog.java:258-264, 1070-1074), stage/replace for atomic CTAS/RTAS via transactions (SparkCatalog.java:272-321), alter (SparkCatalog.java:360-364 → commitChanges at 838-877), rename (SparkCatalog.java:427), drop/purge (SparkCatalog.java:371-419). Each of these maps onto the REST endpoints via RESTTableOperations.commit (the POST-with-requirements commit from the earlier turn).
- Tables load from the catalog as ordinary Iceberg tables, so scans and writes then talk directly to object storage through the client's FileIO — the catalog is only on the control plane (load/create/commit), exactly the thin-design I described. Time travels (AS OF / branch / tag) are resolved from snapshot refs after the catalog load (SparkCatalog.java:184-241, 920-952).

FLINK (flink/v2.3; same across v1.20/v2.2)
Flink uses a serializable `CatalogLoader` that ships from the SQL client / JobManager to TaskManagers, then builds a real catalog on each TM. There's a dedicated serializable loader for REST: `RESTCatalogLoader`, whose `loadCatalog()` instantiates `RESTCatalog` via `CatalogUtil.loadCatalog(...RESTCatalog.class.getName()...)` (CatalogLoader.java:61-63, 149-165). Cloning the loader deep-copies the config (CatalogLoader.java:169-171) so each TM gets its own client instance.
- `FlinkCatalog` (FlinkCatalog.java:107) calls `catalogLoader.loadCatalog()` at construction (FlinkCatalog.java:131), then optionally wraps it in a table `CachingCatalog` (FlinkCatalog.java:132-135). It exposes it for namespace, table, and view operations (`asNamespaceCatalog`, `asViewCatalog`; FlinkCatalog.java:136-139). So Flink SQL statements route through the same REST endpoints.
- Keep state on TM but hold no table: the loader pattern matters because Flink distributes execution; each parallel task constructs the REST catalog locally and talks to the REST service (and storage) from within the cluster.

Both engines therefore rely on the REST catalog the same abstract way: it is their one source of table metadata + commit serialization (the thin pointer-store from the core design), and everything data-path (scanning, writing files, reading manifests) happens downstream against object storage. The only engine-specific REST logic is Spark's purge branch for REST catalogs; the rest is the common catalog adapter boundary.

One note on scope: I read SparkCatalog (v3.5) and Flink's CatalogLoader/FlinkCatalog fully. There are also REST-catalog test harnesses (TestBaseWithCatalog, TestRemoteScanPlanning, TestFlinkRESTCatalogDatabase) that exercise these same paths, but they don't add production behavior beyond what's cited.
