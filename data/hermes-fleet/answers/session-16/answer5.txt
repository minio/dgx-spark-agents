Ten starting points for a new contributor, each with a file:line to read first.

1. What a view is and why it exists — format/view-spec.md:23-27. A view holds no data; it stores a query executed on reference, standardized so views created in one engine (Spark, Trino) can be read from another.

2. The view metadata model — format/view-spec.md:54-65. The spec's required fields: view-uuid, format-version (must be 1), location, schemas, current-version-id, versions, version-log, properties.

3. The in-memory metadata type — core/.../view/ViewMetadata.java:50-87. An immutable interface whose accessors are a 1:1 mirror of the spec fields (uuid, formatVersion, location, schemas, currentVersionId, versions, history, properties).

4. Versions are immutable value objects — api/.../view/ViewVersion.java:32-81. Each version carries its id, schema, summary, representations, and default-catalog/namespace; a changed definition means a new version, never an edit.

5. The only representation type today — api/.../view/SQLViewRepresentation.java:22-33. Stores the SQL text plus a dialect ("spark", "flink", ...); the spec opens the door to more types (api/.../view/ViewRepresentation.java:21-29).

6. How versions get built and deduped — core/.../view/ViewMetadata.java:281-332. addVersionInternal assigns/reuses version ids, enforces "one SQL representation per dialect", and rejects versions referencing unknown schemas.

7. History, retention, and rollback — core/.../view/ViewMetadata.java:461-497. build() bounds retained versions by version.history.num-entries and always keeps the current version, so a metadata file stays self-sufficient for rollback.

8. The commit path / atomic swap — core/.../view/BaseViewOperations.java:105-133. Optimistic commit: rejects stale bases and already-existing views, then defers the actual swap to the metastore's doCommit.

9. The engine-facing API — core/.../view/BaseView.java:113-130. sqlFor(dialect) is the key method engines call to pull the stored SQL back out; the rest of BaseView just delegates to current metadata.

10. How an engine actually uses it — spark/.../source/SparkView.java:61-65 and flink/.../FlinkCatalog.java:862-898. Both adapt an Iceberg View into their own View object and execute sqlFor's result; Flink additionally validates the stored default-catalog/namespace because it resolves into the view's own context.

Suggestion: start at #1 and #3 to get the mental model, then follow #8 → #9 → #10 to see a view travel from metadata to an executing query. The compiler/runtime-produced Immutable* classes (ImmutableViewMetadata, ImmutableViewVersion) are referenced throughout — they're generated by the @Value.Immutable annotation on the *Base* and interface types, not hand-written.
